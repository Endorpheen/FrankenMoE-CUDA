# EXP-2026-09-08-044 — хвост checkpoint 32 токена

Дата: 2026-09-08. Статус: `REJECTED` (`kind=offline-design`, отказ от реализации;
не измеренный performance-отказ). Закрыт по явному решению Игоря 2026-09-08.

## Гипотеза и ожидаемая польза

Увеличить завершающий checkpoint-батч с 4 до 32 токенов, сохранив механизм
checkpoint, чтобы MUL_MAT_ID прошёл существующий CUDA offload-гейт. Польза —
сократить prefill и ожидание первого ответа. Ориентир полезности: ≥3% prefill
без регрессии восстановления. Baseline — принятый EXP-041; диагностические
длительности взяты из EXP-043 и не являются непропрофилированным A/B.

## Проверка без реализации

- В исходниках EXP-041 `tools/server/server-context.cpp`, массив
  `checkpoint_offsets = {4 + n_ubatch, 4}` задаёт завершающее разбиение.
  Для исследованного запроса изменение хвоста даёт 363+32 вместо 391+4.
- В `ggml/src/ggml-cuda/ggml-cuda.cu`, `ggml_backend_cuda_device_offload_op`
  сравнивает размер батча с `op_offload_min_batch_size`; 32 достигает порога 32.
- Перенос позиции checkpoint механически возможен, но не является проверенной
  реализацией: последствия для prefix reuse, restore, коротких промптов и границ
  ubatch не тестировались. После восстановления может потребоваться повторная
  обработка большего суффикса. Checkpoint не отключается.
- EXP-043 атрибутировал последнему CPU-батчу из 4 токенов около 129,5 мс,
  сохранению checkpoint — 16,3 мс (112,592 MiB). Сдвиг позиции сам по себе не
  устраняет сохранение checkpoint. 129,5 мс — стоимость старого участка,
  не гарантированный выигрыш: новый хвост также нужно вычислить.

## Оценка цены и её ограничения

По offline-отчёту локального агента, переданному Игорем: 48 MoE-слоёв, 512 экспертов, top-10; совокупный
размер проекций одного эксперта примерно 1,887 MiB с оговоркой о quant-tier
различиях (точные размеры — EXP-042). Предложенная модель
`unique(n) ≈ 10*n^0,536` оценивает 60–70 уникальных экспертов на слой для
32 токенов, то есть несколько GiB дополнительного staging хвоста. Это
экстраполяция, не измерение маршрутов нового разбиения.

Пример сценария: 32 уникальных эксперта на слой дают
`48*32*1,887 MiB ≈ 2,83 GiB`; при измеренной в EXP-043 полосе
16498 MiB/s передача такого объёма занимает около 176 мс. Это уже сопоставимо
с 129,5 мс старого CPU-хвоста, ещё до учёта gather и вычислений.

Однако 32 эксперта на слой НЕ являются нижней границей: токены могут повторно
выбирать один набор из 10 экспертов. Нельзя вывести распределение unique(32)
из одного aggregate для 391 токена. Нельзя также считать весь staging хвоста
чистой добавкой: первый батч сокращается с 391 до 363 токенов, его selected sets
и transfers тоже изменятся. Gather и H2D могут перекрываться.

Поэтому утверждения «цена заведомо выше выигрыша в 2–4 раза» и «расчёт
однозначно доказывает замедление» не подтверждены. Сценарий показывает риск
дорогого повторного staging, достаточный для решения не тратить ресурсы на
кандидат сейчас. Измеренного бюджета ускорения нет.

## Решение

`REJECTED` как кандидат к реализации: Игорь одобрил закрытие по рекомендации
старшего помощника после проверки отчёта локального агента. Положительный бюджет
пользы не обоснован, повторный staging несёт существенный риск. Код, сборка,
сервер, модель, profiler и A/B не запускались; runtime и память не изменены.
Новые raw-артефакты, тесты и отдельный benchmark JSON не требуются.

Снижение `GGML_OP_OFFLOAD_MIN_BATCH` до 4 не выполнялось и не является
эквивалентной проверкой: меняется offload также для других подходящих операций,
в том числе возможных decode/verify shapes. Его результат и причина выбора
upstream-порога этим анализом не установлены.

Перенос checkpoint после цельного промпта рассмотрен отдельно:
`experiments/checkpoint-post-prefill-decision-2026-09-08.md`.
По этому направлению Игорь также решил сохранить текущие checkpoint.
Ни один из вариантов не требует повторного запуска для закрытия.
Следующее направление не назначено.
