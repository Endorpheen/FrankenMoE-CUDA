# EXP-2026-10-30-086: Apex prefill batch 6144 with preserved context and checkpoints

Status: REJECTED (`kind=model-profile-ab`, qualification memory gate failed). No candidate request or accepted speedup.

## Hypothesis before measurements

With the same unified runtime, 262144 context, all CPU MoE and Q4_0 KV, increasing batch/ubatch together from 4096 to 6144 can reduce the number of complete expert-weight upload rounds for a 32768-token cold-prefix request from approximately eight to six. EXP-084 attributed 54.09% of cold TTFT to H2D. An ideal 25% reduction of that component would reduce TTFT by approximately 13.5%; real compute scaling, final batches and memory can reduce the benefit.

The single variable is the batch/ubatch pair. Model, runtime/library hashes, placement, context, KV format, threads/masks, polling, checkpoints, sampling and prompt tokens are fixed. Reference is the preserved EXP-083 runtime; latest project commit before this experiment is `cf5387dbd8b0c3381222de32e321693f8c4a80dc`.

## M0 and compatibility

No engine source, existing binary, Desktop runtime, unlocked storage, installed profile or legacy build changes. The candidate is a separate launch configuration of the existing runtime. Apex is tested first; a positive result cannot be described as a default for other model architectures. Flint SWA and Apex recurrent checkpoint code remain byte-identical.

Context 262144, all dense layers GPU, all MoE experts CPU, Flash Attention, KV Q4_0/Q4_0, threads 8/16, CPU masks 0f0f/ffff, strict placement, poll 0, one slot, cache-ram 0, ctx-checkpoints 32, mmap, speculation off, EHS off. Main cold request: the same 32768 token IDs, seed 123, temperature 1, top-p .95, top-k 20, min-p 0, EOS respected (`ignore_eos=false`), up to 128 output tokens, top-5 probabilities, native prefix cache enabled with an initially empty slot.

## Pre-stated gates

1. Two qualification starts, control then candidate, one cold request each. Require complete output, no truncation, identical generated token IDs, matching top-5 token IDs and maximum absolute probability delta <=0.001. Record output SHA-256 and differences; do not loosen this threshold after inspecting the candidate.
2. Preserve request-window process swap 0 and no new global swap-out. Record startup separately; stop on OOM or unsafe memory. Candidate GPU headroom must remain at least 512 MiB at resource snapshots. If qualification fails, no performance acceptance.
3. If qualified, perform five manually issued paired fresh-server runs in balanced order, one identical cold request per start. No benchmark script, parallel helper, background build or competing inference. Count each run's actual evaluated tokens and decode separately.
4. Main success metric: median paired reduction of model-reported prefill time >=5%, at least 4/5 wins, and an exact paired-bootstrap median interval above zero. Client TTFT confirms the same direction. Median paired single-response decode regression must be no worse than 2%. Every paired run must satisfy the same correctness/resource checks.
5. Before declaring an accepted profile, check that a 32K branch with a 24K shared prefix still restores correctly and preserves state reuse. Also test a 16384-token branch sharing only 5120 tokens: require valid output and record the actual reused prefix and latency, without hiding checkpoint granularity regressions. A general replacement profile must not lose previously available prefix reuse; any loss prevents general promotion even if cold prefill wins. Keep prior launch commands available and restore the working server after the finite block.

## Pre-measurement clarification

The exact paired-bootstrap interval is computed from all 3125 ordered resamples of the five paired reductions, with linear percentile interpolation at 2.5% and 97.5%. With five distinct observed reductions these endpoints span the observed minimum and maximum; the lower bound must remain strictly positive. This method is fixed before qualification, not selected after seeing performance data.

Before any qualification request, EOS suppression was removed from all three request fixtures following Igor's explicit requirement. The prompt ends in a detailed-analysis request; the 128-token gate remains fixed. If EOS ends the control before 128 tokens, this fixture does not qualify for the pre-stated decode gate and the candidate must not be accepted on that evidence. Prompt token IDs, seed, sampling and top-5 checks are unchanged. The earlier EXP-084 fixtures and evidence remain immutable.

The official upstream server is the helper host during preparation. Model measurements still compare the preserved EXP-083 engine against itself with only batch/ubatch changed; after the finite block, restore the official helper server.

## Results

The first preparation-only control start was closed without a request when Igor prioritized a separate premature-completion diagnosis. Later, qualification ran on the preserved EXP-083 runtime. The helper host was a separately built, clean official upstream `fb5997274ec0d0b4d8fe067eb55f87c0ad405478`; its timings are not substituted for this experiment's reference.

Control batch/ubatch 4096 completed a cold 32768-token request and 128 generated tokens with EOS respected. Server prefill: **22208.067 ms, 1475.500 tok/s**; single-response decode: **30.412 tok/s**. Client TTFT **22.217974 s**, total **26.397844 s**. This one qualification request is not a new median baseline. Independent token/probability structural checks passed.

Control resources: VmSwap 0 before/after, system pswpout unchanged at 8411993, major faults 0. RSS rose from 23053964 to 23782356 KiB; GPU free memory was 1084 then 990 MiB. These are snapshots, not an uninterrupted peak monitor.

Candidate batch/ubatch 6144 failed context initialization before any inference request: CUDA could not allocate **4582326400 bytes (4370.05 MiB)** for the compute buffer. The process exited 1. A second startup explicitly waited for the previous server's confirmed exit; GPU before that retry reported 4472 MiB used and 7401 MiB free. It failed on the identical allocation. This confirms the memory rejection in the actual desktop setup rather than assuming that SIGTERM had completed immediately. No other application was stopped to manufacture headroom.

No candidate response exists, so no model correctness equivalence or speedup can be claimed. The five formal pairs and branch checks were not started after qualification failed. No context reduction, KV-precision change, old-feature removal or acceptance-threshold change was used to rescue the candidate.

## Verdict and next direction
