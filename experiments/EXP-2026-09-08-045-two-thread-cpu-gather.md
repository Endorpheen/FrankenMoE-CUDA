# EXP-2026-09-08-045 — CPU gather в два потока (безмодельный прототип)

Статус: `INCONCLUSIVE` — серия завершена по решению Игоря после четырёх полных пар; исходный gate не подтверждён, интеграция и дальнейшие измерения не выполняются.
Кинд: `kind=prototype-offline` (без модели; performance-заявка о сервере не делается)

## Гипотеза

Scheduler-поток и один постоянный вспомогательный поток могут одновременно копировать
непересекающиеся части одного диапазона в pinned slot, сокращая время подготовки передачи.

Ожидаемая польза — сокращение prefill и ожидания первого ответа. Основание EXP-043:
gather занял 1463,641 мс, а 496,453 мс GPU-простоя совпали с gather. Эти 496,5 мс —
наблюдаемый участок, не гарантированный выигрыш. Ускорения decode не обещаем.

Практический ориентир будущего модельного кандидата — ≥3% prefill (правило решения roadmap).

## Единственная переменная

- A: один поток, обычный `memcpy` в слот (путь принятого EXP-038/041).
- B: два потока суммарно — вызывающий поток и один постоянный помощник.

Сохраняются без изменений: два pinned slots по 16 MiB, исходные диапазоны, padding,
число и объём H2D, порядок CUDA submission, существующий единственный stream,
`cudaEventDisableTiming`, порядок «slot wait → обе CPU-копии завершены → H2D → event».

Не добавляются одновременно: новые memcpy-инструкции (non temporal, SIMD), CPU affinity,
дополнительный stream, увеличение ring, объединение диапазонов, чекпойнт, limited-gap, MTP.

## Прототип

Каталог исходников: `results/archive/EXP-2026-09-08-045/` (отдельный от рантайма).
Каталог сборки: `build/exp045-gather-2t/` (отдельный; рабочий `build/exp041-default-runtime`
не трогается). `work/llama.cpp-integration`, EXP-041, launcher — не меняются.

`exp045_gather2t.cpp` воспроизводит цикл `ggml_backend_cuda_set_tensor_async_pinned_ring`:
`chunk = min(remaining, 16 MiB)`, 2 слота, `cudaEventSynchronize` перед переиспользованием,
`cudaMemcpyAsync` + `cudaEventRecord` на вызывающем потоке, один stream.

Режим B: помощник создаётся один раз вне измеряемой части и живёт всё время прогона.
Задание на chunk публикуется вызывающим потоком (поле payload → release-store счётчика),
граница деления округляется вниз до 64 B (cache line): вызывающий копирует первую часть,
помощник — вторую (несокрывающиеся интервалы и в источнике, и в назначении).
Вызывающий поток обязателно дожидается публикаций завершения обеих частей до `cudaMemcpyAsync`
(accept-load счётчика завершения). Порядок: ожидание освобождения slot → обе CPU-копии →
H2D → событие. Ownership задания — единственный producer (вызывающий), завершение —
release/acquire, остановка — acquire-флаг quit + `join` до `munmap` источника и до
освобождения слотов (lifetime source/slot). CUDA-вызовы только на вызывающем потоке.

Назначение H2D в прототипе: device-арена ограниченного объёма (по умолчанию 256 MiB; фактические
прогоны идут с `--arena 64`, потому что на карте 12 GiB сервер Игоря занимает 9,2 GiB) с
переносом курсора (wrap), чтобы не требовать 21,6 GiB VRAM на карте 12 GiB и не мешать
серверу Игоря. Bytes/calls/порядок/размеры передач это не меняет; стоимость H2D не зависит
от адреса в VRAM. Побайтовая сверка gather выполняется на pinned slot (это и есть объект
эксперимента) плюс device round-trip на отдельном не-wrap регионе selftest.

## Correctness (до измерений)

`--selftest` (обязательно активирует двухпоточный путь; сам факт запуска гейтом не считается):

1. побайтовое совпадение destination с A после synchronize (хэш каждого chunk A vs B);
2. неизменность source и sentinel-областей (checksum источника до/после, 0xCC за концом chunk);
3. нечётные размеры (1, 63, 65, 127, 524801), невыровненные адреса (+1, +3), границы 16 MiB
   (16 MiB−1, 16 MiB, 16 MiB+1), разбиение больших диапазонов (17 MiB, 33 MiB — несколько chunk);
4. многократное переиспользование обоих slots (3 повтора списка кейсов);
5. завершение помощника без обращения к освобождённой памяти (join до `munmap`; остановка
   помощника сразу после завершённого задания).

Дополнительно `--verify` на реальном списке диапазонов: FNV-1a хэш содержимого слота после
каждой gather-копии, полный список A против полного списка B (17886 хэшей, побайтовая сверка).

## Измерения

Вручную, строго последовательно, без параллельных прогонов и фоновой сборки.
Сначала одна предварительная пара A/B. Если полезного сигнала нет или B хуже — останов,
без автоматического перебора числа потоков и порогов. При положительном сигнале —
5 последовательных пар с чередованием A/B и B/A.

Прогрев: один прогон списка диапазонов целиком (исключается из средних) — прогревает касание
страниц page cache; длительность оценена ~3–4 с/прогон (21,641 GiB gather + H2D).
Swap не провоцируем; модель из page cache не вытесняем (читаются те же страницы модели).

Основная метрика: полное время последовательности gather + H2D с финальным drain
(`cudaStreamSynchronize` после последнего события). Дополнительно:
gather wall time (включая передачу задания и ожидание помощника), время ожидания slots,
submit, фактические bytes/calls/chunks, CPU time (caller/helper/процесс), RSS/VmHWM/VmSwap,
результаты по группам размеров (<600 KiB, 600 KiB–1,2 MiB, 1,2–2,5 MiB, ≥2,5 MiB).

CPU-время двух потоков как wall time не суммируется. Синхронизация из цены B не исключается.
Инструментация копий одинакова для A и B. Перед измерениями старший помощник
исправил контроль A: помощник не создаётся. Первоначальный помощник без заданий
активно вращался в pause/sched_yield и расходовал CPU, чего нет в production A.
B сохраняет одного постоянного помощника, созданного вне timed passes.

## Критерий перехода к серверному кандидату

- медианное сокращение полного времени безмодельной последовательности ≥5%;
- победа минимум в 4 из 5 пар;
- все byte-checks проходят;
- VmSwap = 0.

Это только основание предложить интеграцию, не доказательство ускорения сервера.
Если быстрее только изолированный memcpy, а полный gather+H2D не ускоряется — gate не пройден.
Указать дополнительную память помощника (стек 8 MiB по умолчанию, потоковые данные) и риск
конкуренции с CPU-MoE, scheduler и другими потоками.

Модельный запуск, интеграция в принятый runtime и performance-заявление этим ТЗ не
разрешаются. Перед сервером — цель, длительность, число запусков и явное «да» Игоря.
