## Hypothesis

EXP-075 registered a not-yet-covered request on the request thread. A live A/B of the fixed
EXP-075 build measured `-43.17 percent` on the first request after a fresh server start,
because that request paid `cudaHostRegister` for its whole expert set synchronously
(`results/archive/EXP-2026-09-16-075/ab2/`).

PRE-PIN3 tests whether that registration can be moved off the request critical path: serve a
not-yet-covered request through the accepted pinned slot ring (today's default, so no
regression) and pin it in the background, so later requests find it covered and take the
direct path.

## Mechanism

New env `GGML_EXPERT_PIN_ASYNC`, default ON in this build; `0` reproduces EXP-075. With async
on, the request thread never registers:

- a request whose bytes all lie inside existing PHYSICAL registration regions is copied
  directly, clamped to each physical region end (the EXP-075 rule, so a `cudaMemcpyAsync`
  never crosses a `cudaHostRegister` end);
- otherwise the request is copied by nothing on the direct path and is served by the ring in
  full, while each page-aligned uncovered remainder is queued. A request is therefore either
  fully direct or fully ring, never both, so no byte is copied twice.

One background worker, started lazily, drains the queue FIFO and registers under the same
budget (24576 MiB), blacklist, overlap and 8 GiB `MemAvailable` headroom rules. The blocking
`cudaHostRegister` runs WITHOUT the pin mutex; the budget is reserved under the mutex first
and rolled back on failure, so a request never waits for a registration. The worker is
joined in the context destructor before the first `cudaHostUnregister`, and teardown does one
unregister per physical region.

## Live A/B

Protocol: one binary for both arms (`build/exp076-pin-async`), the only variable is
`GGML_EXPERT_PIN_SOURCE` (A = `0`, ring; B = `1`, async on). Port 8087, one fresh server per
run, accepted MTP profile, `-c 196608`. Per run: `warm`, then `p1` (395 prompt tokens), `p1b`
(`p1` again), `p2` (a different 396-token prompt with a partly overlapping expert set), `p2b`
(`p2` again). Between `p1`/`p1b` and between `p2`/`p2b` arm B waits for the worker to report
the queue drained; arm A waits the same length of time. Five pairs, order A/B, B/A, A/B, B/A,
A/B. Raw data: `results/archive/EXP-2026-09-16-076/ab/`.

| point | meaning | arm A median ms | arm B median ms | median paired gain | B wins |
| --- | --- | ---: | ---: | ---: | ---: |
| `p1` | first request after a fresh start | 3016.7 | 4923.7 | -56.16% | 0/5 |
| `p1b` | the same prompt again | 2867.4 | 2119.3 | +27.97% | 5/5 |
| `p2` | novel prompt, first touch | 3491.7 | 3076.8 | +9.59% | 5/5 |
| `p2b` | novel prompt, warm | 3243.4 | 2603.7 | +20.50% | 4/4 |

Completion content was byte-identical in both arms at every point. No run crashed, swim
stayed 0, and arm B released 42852 direct ranges, 0 split ranges and 41784 fallback ranges
over 17955 logical intervals and 28967 physical regions (25 768 853 504 bytes) - the zero in
the split column is the proof that registration left the request thread.

### Reading the first request correctly

The `p1` figure is a ONE-TIME cost per server process, not a per-request property. It is the
price of pinning about 21.7 GiB of source ranges that the process has not pinned yet. In arm
B that work is not on the request thread, but the worker is released while the first prefill
is still issuing its copies, so the two compete for NVMe and CPU and the first request ends
up slower than the `-43.17 percent` of the synchronous EXP-075 build.

The cost is repaid by the very next requests. Extra paid on `p1` is 1907 ms; the three
measured requests that follow save 748 ms (`p1b`), 415 ms (`p2`) and 640 ms (`p2b`), which is
1803 ms - break-even arrives on the third or fourth request, and every request after that is
pure gain. On a long-lived server, which is how the daily profile runs, the first request is
therefore an amortized startup cost rather than a throughput verdict.

This A/B measured five pairs; it did not run a long session, so the exact break-even over
tens of requests is extrapolated from the four measured points, not measured directly. The
trend is monotone in the measured range: the more ranges the worker has pinned, the more
requests take the direct path.

## Verdict

- `CONFIRMED_SESSION_WIN`: with registration off the request thread, every measured request
  after the first is faster than the ring arm (`+27.97 percent` repeat, `+9.59 percent` novel
  first touch, `+20.50 percent` novel warm), content stays byte-identical, and the one-time
  cost is repaid within three to four requests.
- `COLD_START_STILL_OPEN`: the first request itself is still a regression, and worse than the
  synchronous build, because the worker competes with it. Making that request neutral is the
  open follow-up (idle-gated worker start; see `PRE-PIN3b` in the tracker).
- No default runtime change is proposed. The promotion decision is Igor's.
