## 5. How the flag is wired

The flag touches two existing files and adds one new one. The complete diff is
in `patches/`.

`llama.cpp/common/json-schema-to-grammar.cpp`:

```cpp
std::string json_schema_to_grammar_native(const common_json & schema, bool force_gbnf) {
    ...the original body, unchanged...
}

std::string json_schema_to_grammar(const common_json & schema, bool force_gbnf) {
#ifdef FG_GOOSE_JSON_SCHEMA
    (void)force_gbnf;
    return fg_goose_json_schema_to_grammar(schema);
#else
    return json_schema_to_grammar_native(schema, force_gbnf);
#endif
}
```

`llama.cpp/common/json-schema-to-grammar.h` gains the `json_schema_to_grammar_native`
declaration (always) and the bridge declarations (only under the flag).

`CMakeLists.txt` (staged project):

```cmake
if(FG_GOOSE_JSON_SCHEMA)
    add_library(fg-goose-json-schema OBJECT goose-gen/json-schema-grammar.c)  # one object
    set_target_properties(fg-goose-json-schema PROPERTIES C_STANDARD 11 POSITION_INDEPENDENT_CODE ON)
    target_compile_options(fg-goose-json-schema PRIVATE -w)
    target_sources(llama-common PRIVATE common/fg-goose-schema-bridge.cpp)
    target_compile_definitions(llama-common PRIVATE FG_GOOSE_JSON_SCHEMA=1)
    target_include_directories(llama-common PRIVATE ${CMAKE_CURRENT_SOURCE_DIR}/goose-gen)
    target_link_libraries(llama-common PRIVATE fg-goose-json-schema)
endif()
```

Properties that matter for the production rule ("a new feature's flag exists
only to disable it"):

- OFF is the default and produces byte-identical grammar text to the base build;
- the native converter is compiled in both configurations, so switching the
  flag off is a rebuild, not a revert;
- no translation unit is edited at run time and no native call is deleted.

## 6. The seam this stage cannot remove

`json_schema_convert` does not parse JSON: it consumes a flat node table
(`meta` 11 int64 per node, `props` 4 per property, `vals`, `strs`, `sdir`).
The host must therefore build that table from the parsed schema, and that is
`build_node`/`fill` in `common/fg-goose-schema-bridge.cpp` — about 380 lines of
C++ that mirror the native document walk (kind selection, `$ref` resolution with
a path map, `additionalProperties` modes, exclusive-bound folding, format
classification). It is the honest price of this slice: the Goose module owns the
GBNF rule catalogue, the pattern translator, integer-bound grammar and the
sorted rule text, while the host still owns "JSON document -> node table".

Consequences recorded for the next slice:

1. The bridge allocates roughly 4.4 MB of scratch per call (three 1 MiB byte
   buffers, `1<<18` int64 work buffer, four 4096-entry int64 tables). Correct,
   but not acceptable on a request path; a pooled buffer is needed before any
   server wiring.
2. Error parity is not proven. Goose records the first error internally and
   `json_schema_convert` returns `-1`; the native path throws
   `std::invalid_argument("JSON schema conversion failed:\n" + ...)` with every
   error. The bridge throws a generic `invalid_argument` instead. The exports
   `conversion_failed` / `conversion_warning` exist in the module but are not
   wired.
3. `force_gbnf` is ignored on the ON path. With `LLAMA_LLGUIDANCE=OFF` (the
   configuration measured here) the native path ignores it too, so there is no
   behaviour change today, but an LLGuidance build would lose the
   `%llguidance` branch.
4. The gate corpus is 30 schemas / 182 rules, the EXP-570 corpus. It is the
   same set the module was accepted on; it does not cover `format` values that
   the native converter rejects, external `$ref`s, or `$defs` naming variants.
5. No model-level check: S1 acceptance also requires identical model output for
   the same request, which needs the GPU runtime and Igor's explicit approval.
   Nothing in this stage claims a step toward that yet.

## 10. What is still open

1. **The host seam.** The JSON document walk in `fg-goose-schema-bridge.cpp`
   is not Goose yet. The next slice should move it into the module (the file
   already exports `schema_build` for the older flat-document contract) so the
   entry point consumes `common_json` directly.
2. **Scratch buffers.** 4.4 MB per call, allocated with `std::vector`; needs a
   reused/pooled arena before any request-path use.
3. **Error and warning text.** `conversion_failed`/`conversion_warning` are not
   wired; the thrown message differs from the native one. A differential gate
   on invalid schemas is not written.
4. **`force_gbnf` / LLGuidance.** Ignored on the ON path; harmless only while
   `LLAMA_LLGUIDANCE=OFF`.
5. **Coverage.** 30 schemas, 182 rules. The native converter accepts more
   keyword combinations than the module was gated on; a wider corpus has to
   come with the next slice.
6. **Other symbols the runtime still needs from this family.** Only
   `json_schema_to_grammar` is switched. `build_grammar` (used by chat tool
   handling through `common_grammar_builder`) and
   `common_schema_converter::visit` remain native and keep their own error
   contract; a full switch would need the module to expose a rule-builder
   callback interface instead of a complete text.
7. **Gate convention.** The repository expects the gate at `-O1`; this gate
   runs at `-O2` because it links the Release library. The generated Goose
   object is compiled at `-O2` with `-w`.
8. **Model-level parity.** Not attempted: no server, no model, no GPU. The
   S1 acceptance of "identical model output" is untouched.
9. **Second module of S1.1** (`json-escape`, the escaping path) was not
   staged here; `goose/jinja/json-escape.goose` is one 19,097-line unit with 92
   exports and needs its own seam decision.
