# EXP-2026-09-07-042 — limited-gap H2D coalescing (PRELIMINARY ANALYSIS)

Статус: PRELIMINARY_ANALYSIS. Не executed-experiment, не performance-claim.
Фаза: оценка направления из audit A7 (docs/AUDIT-2026-09-06.md:107, "limited-gap
H2D coalescing"). Только offline: сервер, модель, profiler, build и исходники рантайма
не трогали; авторитетные размеры взяты из метаданных GGUF (офлайн, без запуска).
Результат этапа: бюджет ускорения не установлен, знак эффекта неизвестен;
автоматического разрешения писать оптимизацию нет.

## Гипотеза

Scheduler уже склеивает строго соседних экспертов (ggml-backend.cpp copy_experts,
условие `id == last_id + 1`). Идея: разрешить захватывать небольшой промежуток с
невыбранным экспертом, чтобы две H2D-передачи слить в одну непрерывную. В отличие от
отклонённого EXP-033 (packing + device scratch + byte scatter + ID remap), здесь прямое
непрерывное копирование в прежние offsets, scatter/remap не нужны. Ожидаемая польза
относится к prefill; decode ускорения идея не обещает.

## Новизна

Не повторяет ни принятый pinned ring (EXP-038..041, сохранил число копирований
calls=chunks=17886), ни отклонённый packing/scatter (EXP-033). Отличается конкретным
offline-расчётом числа передач и дополнительных байтов.

## Два самостоятельных кандидата порога (оба равноправны)

Это два разных определения «небольшого пропуска»; ни одно не опровергает другое, и
обязательного перехода от байтового порога к числу экспертов нет.

1. Кандидат A — фиксированный байтовый порог: слить две передачи, если байтовый
   зазор между ними ≤ 512 KiB и объединённый span ≤ slot (16 MiB). Результат:
   12 316 передач (−31,14%) при +2 785 MiB (+12,57%), ≈0,50 MiB на устранённый вызов.
   Реализуем прямо в scheduler: сравнить байтовый зазор между соседними range.
2. Кандидат B — пропуск по числу экспертов: слить, если между диапазонами ≤ N
   пропущенных экспертов (любого размера) и span ≤ slot. При N=1: 9 434 передач
   (−47,25%) при +5 296 MiB (+23,90%), ≈0,63 MiB на устранённый вызов.

Кандидат A дешевле по доп.байтам, но склеивает меньше (у down-проекций зазор одного
пропущенного = 921 088 байт > 512 KiB, поэтому down однократные пропуски A не трогает).
Кандидат B склеивает больше ценой больших байтов. Выбор порога — отдельное решение,
не следствие расчёта.

Полезный факт о зазоре: размер каждой передачи уже включает trailing padding 512 байт
(`min(expert_size,512)`, кроме последнего expert). Байтовый зазор при пропуске ровно
одного эксперта = `expert_size − 512` (gate/up 524 288; down 921 088; blk.2 gate/up 703 488).

## Размеры expert-slice (подтверждены из GGUF, не из GCD журнала)

Авторитет = `nb[2] = n_bytes // ne[2]` из метаданных GGUF (`models/qwen38/UD-IQ3_XXS`).
У всех expert-tensor'ов форма одинаковая (gate/up `2560x640x512`, down `640x2560x512`),
но тип квантизации разный — модель гетерогенная (expert-tier):

| role | ggml_dtype | nb[2] байт | слоёв |
|------|-----------:|-----------:|------:|
| down | 20 | 921 600 | 48 |
| gate | 22 | 524 800 | 47 |
| up   | 22 | 524 800 | 47 |
| gate | 21 | 704 000 | 1 (blk.2) |
| up   | 21 | 704 000 | 1 (blk.2) |

Третий размер (704 000) — слой blk.2, у которого gate/up лежат в другом quant-tier
(ggml_dtype 21 вместо 22) при неизменной форме; отсюда больший байтовый шаг expert.
Предупреждение: НОД наблюдаемых offsets в журнале — только верхняя оценка expert_size,
сам по себе точный `nb[2]` не гарантирует (мог бы быть и делитель). Здесь GCD случайно
совпал с GGUF по всем 144 tensor, но расчёт опирается на GGUF.

## Безопасность по исходникам EXP-041 (условная)

Источник истины: `patches/pinned-ring.patch` sha256 e1e6803... (byte-identical принятому
EXP-038) + `work/llama.cpp-exp041/ggml/src/ggml-backend.cpp` (1699-1741) и `ggml-cuda.cu`.

- Destination `input_cpy` — постоянный device weights-tensor, expert по offset
  `id*expert_size`. Пропущенный expert пишется СВОИМИ настоящими host-байтами на СВОЙ
  offset. Не compact/scratch, offset-идентичность целая, scatter/remap нет.
- Lifetime (EXP-037 dependency_map): dst перетирается per split; последний потребитель —
  MUL_MAT_ID того же split на том же stream; следующее перетирание — следующий запрос.
- Конфликта за пропущенные области нет: они не в `used_ids` и не читаются этим узлом;
  перезапись корректными байтами безвредна; тот же stream упорядочивает запись.
- Ring при graph capture возвращает false и откатывается на set_tensor_async; любое
  объединение обязано сохранить откат.

Инварианты, при которых объединение остаётся безопасным (иначе — нет): (1) тот же tensor и
те же offsets (offset = id·expert_size), НЕ упаковывать; (2) тот же compute stream + событийная
дисциплина кольца; (3) объединённый span ≤ slot (16 MiB), иначе ring дробит на несколько
чанков/событий и экономия вызова размывается; (4) `padding_end` для объединённого `last_id`;
(5) `last_id < n_expert`. Совпадения адресов в журнале — НЕ доказательство безопасности;
доказательство — инвариант кода + lifetime-вывод EXP-037.

## Окупаемость — знак НЕ установлен

Расчёт даёт только две величины на кандидата (число устранённых вызовов и доп.байты);
время из них не выводится без замеров на доставленном EXP-041 рантайме.

- Экономия на вызове = pinned submission + `cudaEventRecord` + ring bookkeeping.
  EXP-037 дал лишь ПРЕДСКАЗАНИЕ о submission (95-380 ms на 19013 вызовов = 5-20 µs/вызов).
  Это НЕ измеренная верхняя граница всей экономии: events/bookkeeping могут быть и больше,
  и меньше; прямого замера нет.
- Добавка = доп. CPU-gather memcpy + доп. PCIe/H2D + доп. запись на device. Их НЕЛЬЗЯ
  складывать как обязательную прибавку к wall time: ring перекрывает два слота, gather
  может перекрываться с потреблением GPU, и у H2D/gather может быть незанятая полоса.
- Утверждение «submission ушёл с критического пути» результатом ускорения ring НЕ
  доказано: EXP-038 дал +13% при неизменном числе вызовов, но это не измеряет остаточный
  вklad отдельного вызова после ring.

Корректный вывод один: знак эффекта неизвестен. Ни «в плюс», ни «в минус» утверждать
нельзя. Порог окупаемости (breakeven) требует недостающих замеров (см. ниже). Старые
pageable-тайминги (164,2 µs/вызов) на новый рантайм не переносятся.

## Недостающие данные для оценки окупаемости (по доставленному EXP-041)

1. Замеренная стоимость одного вызова на pinned-ring: `cudaMemcpyAsync` submit +
   `cudaEventRecord` + ring bookkeeping в µs/вызов (не предсказание EXP-037).
2. Замеренная ширина gather-полосы (memcpy host->pinned), её доля на критическом пути и
   наличие незанятой полосы, чтобы поглотить +12,57%..+23,90% без роста wall time.
3. Наличие у GPU H2D idle-headroom в pinned-сборке (запас 1832 ms из EXP-037 — PRE-ring,
   после ring недействителен).
4. Фактическое распределение объединённых диапазонов на текущем scheduler/модели, чтобы
   подтвердить 12 316 (A) / 9 434 (B) для текущего layout.

## Вердикт этапа

Бюджет ускорения не установлен, знак эффекта неизвестен. Offline-расчёт доказывает
сокращение ЧИСЛА передач, но НЕ времени выполнения. Реализацию и модельный A/B начинать
рано; требуется п.1-3 (замеры на доставленном рантайме) до решения о candidate. Автоматического
разрешения писать оптимизацию этот документ не даёт. Направление не выбрано как приоритетное.
