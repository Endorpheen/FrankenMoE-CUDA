Cause of the original 30/64 report: the comparison offsets were dense (`dst[i]`)
instead of routed (`r*nb0 + route0*nb1 + route1*nb2`), so rows that were not
written were compared against values from another slot. The kernel itself is
correct on this case both as the AVX2 unit and as the scalar fallback.

Real defect found while reproducing: the C shim sized the dst slice as
nb0*ne01 + nb1*cne1 + nb2*cne1, which is smaller than a sparse route offset and
made the scalar path abort with "array index out of bounds". The slice now
covers max(route0*nb1 + route1*nb2) + (ne01-1)*nb0 + 4.

== Group 0 investigation (repro_group0) ==

The shipped repro compares against `ggml_vec_dot_q4_K_q8_K(n, &s, 0, x, 0, y, 0, 1)`.
On this host that call returns 0 for every row, so its "reference" is empty: rows
whose weights are zero match trivially (the 64/64 of groups 1-7) and the real rows
of group 0 look wrong, with row 2 "constant" at the kernel value 0.063255541.

Independent check of the same data (per-block decode, Python) gives row 2 =
0.0632555146 and row 3 = -0.200779682, i.e. the file's expected values, and the
kernel reproduces them bit-exactly.

Corrected repro `src/repro_group0_fixed.cpp` computes the reference directly from
the block format with the same float order as the native microkernel
(d*s1, fmaf(-dmin,s2), fmaf(d_act,res,acc)). Result on failing_case.bin:

  group=0..7 rows 64 each: eq=64/64 every group, total diffs=0, exit=0
  same numbers with the scalar object (FGOOSE_SIMD_CPU_DISABLE)

So no kernel defect exists for this case; the defect was in the repro's reference
call. `repro_group0_fixed` is now part of run_mmid_check.sh.
