# EXP-2026-09-09-051 — проект: два варианта CUDA Graph на ключ (формы 1/3 драфта)

Статус: `DONE` (`kind=design`, 2026-09-09, без запусков). Задание Игоря после EXP-050:
исследовать отдельное сохранение графов для форм 1 и 3 (не дробление catch-up на три
однотокенных прохода — это увеличило бы число вычислительных вызовов и могло потерять
пользу батчинга); до реализации проверить четыре пункта; синки и D2H сохраняются.
Гипотеза Игоря: два варианта уменьшат rebuild/capture и CPU-расходы на запуск draft;
потенциально ≥2% decode, но бюджет нужно оценить — draft лишь часть шага.

## Формулировка решения

Значение карты `cuda_graphs` (ключ — указатель `nodes[0]`, common.cuh:1464) становится
массивом слотов-вариантов, а не одним объектом `ggml_cuda_graph`. Слот = {graph, instance,
warmup_complete, node_props-снимок, uid, last_used}. Решение на вызов: перебрать слоты,
найти готовый instance с `update_required == false` → replay; иначе жертва (пустой слот или
LRU) → warmup + capture в него. Ключевое отличие от сегодня: снимок соседнего варианта
больше не перезаписывается чужой формой — именно перезапись одним снимком на ключ убивает
replay драфта (EXP-050: цикл reset→unstable→capture, 0 launch на 353 вызова).

Совместимость и корректность не меняются: единственный критерий — побайтовая идентичность
`node_properties` всех узлов (тот же memcmp, что сегодня). Никакого хэша размеров в проект
не вводится. Управление: env `GGML_CUDA_GRAPH_VARIANTS` (1 = сегодняшняя семантика, default
для совместимости с baseline; 2 = варианты; при приёме — default 2).

## Четыре пунктов проверки (задание Игоря)

1. Меняет ли L1-rebuild адреса и пригодность сохранённых графов — нет, адреса стабильны.
   Код: `llm_graph_result::reset()` ре-инициализирует ggml-контекст на том же
   `buf_compute_meta` (llama-graph.cpp:1347–1360) → адреса тензорных метаданных и `nodes[0]`
   сохраняются. Эмпирика EXP-050: оба ключа драфта держали одни адреса все 351 вызова при
   173 L1-rebuild; target-ключи после единственного verify-rebuild продолжили launch.
   Остаточный риск: diff EXP-050 печатает только первое несовпавшее поле, за ним могут быть
   скрытые расхождения — на корректность не влияет (полный memcmp отклонит несовпадение и
   уведёт слот в recapture), на эффективность проверяется гейтом и A/B.

2. Свойства помимо формы: сегодня и в проекте совместимость = node_count + полный
   `ggml_tensor` каждого узла (type, buffer, ne[4], nb[4], op, op_params, flags, src[] с их
   data/ne/nb, view_src, view_offs, data, name, extra, padding) — ggml-cuda.cu:2927,
   common.cuh `node_properties`. Хэша размеров недостаточно и не нужно: слот выбирается
   перебором ≤2 с полным сравнением, «вариант» — индекс слота, а не хэш. Легитимная
   периодическая смена формы внутри варианта: `kq_mask ne[0]` растёт с KV с паддингом 256
   (llama-kv-cache.cpp:1250–1264) → один recapture на ~запрос — норма.

3. Ограничение двумя вариантами и память: слотов ≤ V (default 2). Драфт-бэкенд: 2 ключа × 2
   = ≤4 instance (графы по 116/63 узла; порядок десятков–сотен КБ VRAM, точная цифра — при
   реализации) + ≤4 снимка × ~179 узлов ≈ 0,2–0,4 МБ host (~1 КБ/узол). Target-бэкенд:
   49 ключей, в установившемся decode одна форма — второй слот лениво не занимается; на
   стыке prefill(36)/verify(3) максимум +49 instance (~1–2 МБ VRAM, оценка) с бонусом replay
   prefill. По уточнению Игоря оценка недостаточна: фактический лимит дополнительных host/device allocations измеряется в EXP-052 (точная host-арифметика sizeof(node_properties)×n_nodes×слоты + дельта cudaMemGetInfo вокруг захватов, оговорка о страничной гранулярности); второй слот может появиться и у target — считается счётчиком слотов в реализации. LRU внутри ключа; прежний
   10-с sweep ключей (common.cuh:1468–1489) действует и на слоты. Инвалидация: провал
   ExecUpdate — destroy instance только слота-владельца, сосед живёт.

4. Какая доля расходов исчезнет (бюджет — экстраполяция из EXP-043/048/050, не измерение):
   шаг 124,8 мс (14600,79 мс eval / 117 шагов). Драфт-бэкенд на шаг: 3 вычислительных
   вызова × (116+63) = 537 узлов — сегодня прямые запуски + 2 capture; станет 6 graph
   launch (2 сплита × 3 вызова). Экономия CPU ≈ 531 × 3,08 мкс (mean `cudaLaunchKernel`
   EXP-043) ≈ 1,64 мс/шаг; плюс исчезают 2 capture+instantiate/шаг (оценка 0,1–0,5 мс,
   прямого измерения нет). Остаётся: 2 L1-rebuild/шаг (build-стоимость не измерена, бакет
   хост-сериализации EXP-048) и полезное вычисление. Итого L2-only ≈ 1,7–2,1 мс ≈ 1,4–1,7%
   шага — ниже порога ≥2%; расширение на L1 (две цепочки результата) добавило бы ~0,4–1 мс
   → 1,7–2,5%. Оговорка (урок EXP-046): серверный эффект может превысить локальную оценку.
   Решение о реализации и о L1-расширении — по результату A/B.

## Lifetime (сводка)

Создание: первый вызов формы занимает пустой слот (direct), второй подряд идентичный —
capture + instantiate. Использование: replay при полном совпадении свойств слота.
Вытеснение: внутри ключа — LRU по last_used (≤V слотов); между ключами — прежний 10-с sweep.
Инвалидация: property-mismatch — тёплый сброс своего слота (теперешний reset ветки,
ggml-cuda.cu:4655–4658); провал ExecUpdate — destroy instance слота. Выключение:
`GGML_CUDA_GRAPH_VARIANTS=1` возвращает сегодняшнее поведение один к одному.

## Уточнения Игоря (приняты 2026-09-09, условия реализации EXP-052)

Решение: L2-only первым шагом; L2+L1 одновременно усложнит проверку и скроет источник
результата. Ожидаемые 1,4–1,7% ниже порога — это исследовательский кандидат, не обещанные
≥2%. L1 автоматически не добавлять, даже если выигрыш окажется меньше 2%.

1. Стабильность ключа не доказывает lifetime всех адресов захваченного графа: полный memcmp
   полезен, но отдельно проверяются device-буферы, аргументы kernels и временные allocations
   после L1-rebuild. Как проверяется: (а) код-разбор — аргументы kernels у GGML происходят
   из полей тензоров (data-указатели, ne/nb), которые входят в node_properties, и из
   cublas-workspace/pool-адресов бэкенда; (б) безмодельный гейт со сценарием «rebuild графа
   на том же буфере метаданных (как reset() в llama) → replay без recapture → результат
   равен контролю»; (в) эмпирика EXP-050: 173 захвата d2 после rebuild — свойства, включая
   data-указатели, совпали побайтово. Остаток риска (временные pool-адреса) закрывается
   полным memcmp: любое расхождение уводит в recapture, неверный replay невозможен.
2. Память — только оценка (см. правку в п.3): измеряемый лимит вместо «пренебрежимо»,
   счётчик слотов по бэкендам (target включён).
3. Гейт вытеснения/восстановления — расширенный список сценариев (каждый — сравнение
   результата с контрольным путём без графов): чередование 1→3→1→3 (обе формы на launch);
   третья форма (LRU-вытеснение, правильность после recapture); смена указателей при той же
   форме (новый ключ, first_call/capture); update-failure (принудительный провал
   ExecUpdate через тестовый env-шов, destroy только слота-владельца, сосед живёт);
   sweep/teardown (10-с выселение ключей, чистый деструктор без CUDA-ошибок).

## Что не меняется

Синки, D2H, алгоритмы, capture-legality (`ggml_cuda_graph_check_compability` на уровне
ключа), пути данных. Локализация правки: common.cuh (слот + карта) и ggml-cuda.cu (выбор
слота в автомате решений), ~60–100 строк; диагностические поля EXP-050 — на слот.

1. Безмодельный гейт: расширение `exp050_synth.c` — чередование двух property-наборов на
