# EXP-2026-09-15-062: pinned ring depth 3 (PRE-1)

Status: `ACCEPTED` (2026-09-15).
Kind: `performance`.

This card records a build-flag A/B that has already been run. The raw data is under
`results/archive/EXP-2026-09-15-062/ab/`. The card itself starts no server, loads no
model, builds nothing and runs no curl. It is the written verdict for the
candidate tracked as PRE-1 in `experiments/HYPOTHESES-2026-09-15-runtime-speed.md`.

## Hypothesis

A third 16 MiB pinned ring slot raises the pinned expert-upload pipeline from depth
2 to depth 3, so the CPU can stay one extra chunk ahead of the in-flight H2D copy.
Part of the 326.679 ms `expert_slotwait` union measured in EXP-043 (with
`cudaEventSynchronize` at 321.093 ms inside it) should disappear, and bulk-prefill
latency should fall.

The accept gate, fixed before the runs in the design note: median paired prefill
gain >= 3%, at least 4 of 5 pairs won, decode regression no worse than 2%, completion
content byte-identical, and `VmSwap == 0` everywhere.

Design source: `experiments/designs/exp057/D4-ring-depth3.md`. Prior measurement
this builds on: `experiments/EXP-2026-09-07-043-prefill-bottleneck-profile.md`.

## Protocol (manual, one server at a time)

- Accepted profile, port 8087 (kept separate from the daily 8081 server).
- `GGML_EXPERT_RING_GATHER2T=1` pinned in both arms for every run, so the two-thread
  CPU gather is constant and is not a hidden variable.
- One fresh server process per run, one warmup request, then one measured request.
- Six pairs, alternating arm order and starting with A/B: A/B, B/A, A/B, B/A, A/B,
  B/A. Pair 1 (A1 then B1) is the cold page-cache warmup pair and is excluded. The
  five scored pairs therefore run in the order B/A, A/B, B/A, A/B, B/A.
- Every run is 395/395 prompt tokens and 48/48 generated tokens with
  `stop_type` `limit`; no request was repeated inside a server session.
- No profiler runs alongside a timed run, and no two servers run at the same time.

## Paired results

`prompt_ms` is `timings.prompt_ms` for the fixed 395-token request. Pair gain is
`100 * (A - B) / A`, so a positive number means the depth-3 candidate is faster.

| --- | --- | --- | --- | ---: | ---: | ---: |
| 1 (excluded) | A/B | A1 | B1 | 7672.011 | 3192.322 | not scored (cold page cache) |
| 2 | B/A | A2 | B2 | 2843.266 | 2708.144 | +4.752% |
| 3 | A/B | A3 | B3 | 3305.376 | 2924.041 | +11.537% |
| 4 | B/A | A4 | B4 | 3039.153 | 2628.321 | +13.518% |

- Median paired gain: +11.537%.
- Wins: 5 of 5 pairs favor B.
- Median prefill latency: A 3039.153 ms, B 2708.144 ms.
- Arm-median change: B is -10.891% versus A, a saving of 331.009 ms on the median.

## Causal note

The control's median prefill time is about 336 ms above the candidate's (arm medians
3039.153 ms to 2708.144 ms; the paired median gain is +11.537%). This is the same
magnitude as the EXP-043 `expert_slotwait` union of 326.679 ms, and it is the only
component EXP-043 identified as directly addressable by pipeline depth. The
direction of the effect matches the hypothesis: with three slots the caller returns
to a slot later, so more of the per-depth wait is hidden behind the previous H2D.
The saving is a fraction of the window, as the design note predicted, but it is
large enough to clear the prefill bar on this workload.

## Memory impact

- Depth 2 (control): 2 x 16 MiB = 32 MiB pinned host.
- Depth 3 (candidate): 3 x 16 MiB = 48 MiB pinned host.
- Delta: +16 MiB pinned (16,777,216 bytes), well within the approved G3 budget of
  48 MiB.

The extra slot is a fixed pinned allocation: it reduces pageable RAM by 16 MiB on a
64 GB host, which is immaterial here, and it allocates nothing on the device. No
other buffer, cache or VRAM reservation changed.

## Verdict: ACCEPTED

Every pre-registered gate passed:

- Median paired prefill gain +11.537%, above the 3% bar.
- 5 of 5 pairs favor the candidate.
- Decode is +2.247%, inside the 2% regression bound.
- Content is byte-identical across all runs.
- `VmSwap == 0` in every telemetry sample.
- Pinned budget rises from 32 to 48 MiB, inside the approved G3 budget.

PRE-1 is accepted on these numbers. Delivery as the default runtime is a separate
step and is not part of this experiment: per Hard rule 10, a new default-on change
gets its own minimal commit after this acceptance, and the flag stays as the way to
disable the feature, never to opt in. This card does not build, commit or flip any
default.
