Root cause (the deliverable Igor asked for)
-------------------------------------------
The draft context alternates ubatch shapes every speculative step:
catch-up of accepted tokens (n_tokens=3) vs draft generation (n_tokens=1).
- L1: llm_graph_params::allow_reuse requires ubatch.n_tokens equality
  (src/llama-graph.cpp:1487), called from llama_context::process_ubatch
  (src/llama-context.cpp:1419) -> 2 of 3 draft ubatches rebuild every step.
- L2: the CUDA graph key is cgraph->nodes[0] (ggml/src/ggml-cuda/ggml-cuda.cu:4605);
  update_required memcmps node_properties incl. node[0].ne (ggml-cuda.cu:2927);
  warmup needs >=2 consecutive identical calls (ggml-cuda.cu:4627-4634).
  The 1<->3 alternation flips node[0].ne[1] (and ne[2]) every call, so warmup
  never converges for the draft's 2 splits: 0 replays for the whole run plus a
  capture+instantiate every step whose instance is destroyed one step later.
The target context is unaffected at both levels.

Cost per spec step (diagnostics only, not a speedup claim):
  draft backend: 2 direct executions of 179 nodes (116+63) + 1 graph capture
  (with instantiate) + 2 full L1 graph rebuilds.

Remediation directions (Igor's decision, nothing implemented):
  (a) run catch-up as three n_tokens=1 ubatches -> all draft calls shape-1,
      L1 chain stable, L2 warmup converges after step 2;
  (b) namespace graph results / CUDA graph keys by shape hash instead of
      nodes[0] pointer;
  (c) leave as is.
