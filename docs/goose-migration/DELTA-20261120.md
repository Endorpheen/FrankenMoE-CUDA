# What changed in the runtime itself, 2026-11-20

One page, because the day produced a lot of documents and the question Igor keeps asking is narrower: did
the runtime get better, and did it keep its speed.

## 1. The baseline changed, and the speed did not

| | previous baseline | new baseline |
|---|---|---|
| artefact | EXP1476 (198 doors) | working build (200 doors) |
| decode, paired run | 61.36 | **61.44** |
| prefill, paired run | 2906.2 | **2918.1** |
| VRAM / response hash | 9465 MiB / `c2ff42cc1219` | identical / identical |

Two more doors, same answer, fractionally faster on both axes. The run that measured the old baseline
today gave 61.36 against a recorded 62.86 - the session is cooler than the record was, and that is why the
comparison had to be paired.

## 2. Two Goose decisions were proven to execute, not merely to exist

- **grammar**: `FG171_GRAMMAR_SIZES` and `FG171_PREFILTER` printed six times each during a live
  constrained request, and the constrained answer was valid. The markers sit inside the hook after
  `fg_grammar_enabled()`, so they cannot print on the native path.
- **sampler**: `FG171_TOP_P` (16) and `FG171_DIST` (6) during the baseline run.

Both were previously "verified" by symbol tables and test gates only.

## 3. The JSON path went from absent to working

Yesterday: the shipped library carried neither half. This morning: the adapter in `libllama-common`, the
parser door nowhere. By evening: the door linked, but `json_parse` failed at run time for two reasons that
only a probe could show:

- the generated module **declares** `gs_abort`, `gs_panic`, `gs_idxfail` and defines none of them - the
  host must supply the runtime;
- the door refuses to answer before `goose_init`, and a caller that only knows the symbol name cannot be
  asked to initialise it.

Fixed by compiling this module with `--standalone` (it then carries its own runtime) and giving the bridge
a constructor that runs the init when the library loads. Verified in isolation: `json_parse` returns 0 on a
real document. The swap test passes on a set that carries both halves - seven texts, strict mode, no
fallback.

## 4. One claim withdrawn

I wrote that the shipped tokenizer's carrier never calls its doors. Wrong: it calls 16 of them through
`llama_goose_*` wrappers, and my grep could not see those names. Withdrawn in the same hour, with the
correction written into the record.

## 5. The compiler question answered with a fact, not a preference

`fried-goose-v0.2.0-preview-openwing` does support `export fn` and `--header` - checked by compiling a
sample - but it has **no `--standalone`**, and every build path here compiles a 156-module unit with it. So
the pinned compiler stays; the new line is the target for a per-module flow, not a drop-in.

## What did not change

No native code was deleted. Nothing was published. The four axes of the accepted profile were not touched.
And every figure here comes from a paired run or from a marker printed by the code that decided.
