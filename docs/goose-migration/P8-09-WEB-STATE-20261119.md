Nineteen doors in total.

## Who calls them

**One of the nineteen**, and it is today's own work: `key_authorize` is now called from
`server-http.cpp` under `FG_API_KEY_GOOSE` (see below). The other eighteen have no call site.
Searching the shipped server sources and the reconstructed runtime for each exported name returns
nothing: `vendor/flint/tools/server/server-http.cpp` has no Goose reference of
any kind, and it is the file that owns static serving, MIME types, ETags, CORS and the API-key
check in the shipped binary. The UI itself is embedded at build time - the build log of this
morning's candidate says `UI: embedded 75 assets` - and served by that same native code.

## What the requirement needs

Switching the serving path to these four modules, then a gate over the same inputs: the asset
table, the MIME lookup, the ETag bytes and the API-key verdict. The differential is well defined
because each door is a pure decision:

- `web-assets`: the asset index and the path lookup, including a miss (the 404 body);
- `mime-table`: extension to content type, including the unknown extension;
- `asset-etag`: the tag for the same bytes, and the conditional-request comparison;
- `api-key-policy`: the verdict for a present, absent, wrong and empty key, and for the "disabled"
  setting.

## What is not claimed

That the interface works through Goose, or that any of this is measured. The nineteen doors are
composed and called by nothing, which is the case rule 33 warns about, and the served path is
unchanged from before the port.

## Why "wire the four modules" is a refactor, not a patch (checked 2026-11-19)

Static files are not served by project code: `server-http.cpp:380` calls
`srv->set_mount_point(api_prefix + "/", public_path)` and cpp-httplib does the rest - path
resolution, the MIME lookup, the `Last-Modified`/`ETag` headers and the 404 body all live inside the
library. Our code sees the request only after the library has decided it is not a static file.

So switching `mime-table`, `asset-etag` and `web-assets` on is not a call added to an existing
branch: it means **replacing the mount point with a handler** that resolves the path itself, asks
`mime_of` for the type, asks the ETag door for the tag and the conditional comparison, and produces
the 404 body from the asset table. That is the shape of the work, and it is why it has not been done
as a five-line change.

`api-key-policy` is the exception: the key check happens in project code, so it can be wired
independently of the static-file path.

## What that changes about the next step

Order, cheapest first:

1. `api-key-policy` (8 doors) - the verdict is already in a branch the project owns;
2. the ETag comparison, which is a decision over two strings and can be shadowed before the mount
   point is touched;
3. the mount-point replacement, last, because it is the one change that can break serving.

The differential for each is already written above; the mount-point replacement additionally needs a
routing test over the real asset set, which is a server run.
