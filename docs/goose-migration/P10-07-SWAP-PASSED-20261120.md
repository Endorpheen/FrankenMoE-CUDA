# The JSON swap works: adapter and Goose parser, seven texts, no fallback

The two halves existed in two different artefacts - the working build carries `json_parse` in `libllama`,
the path-A candidate carries `fg_json_adapter::to_tree` in `libllama-common`, and neither carried both.
Putting them together answers the question P10-07 was stuck on.

## The set

`builds/flint-acc/run-json` = baseline B's files with the candidate's `libllama-common` in place of its own.
Self-contained check: **ok**.

## The swap test

```
== 1. flag off                                   ok (nlohmann)
== 2. flag on, strict    json swap: goose=1 texts=7 failures=0
== 3. flag on, strict, no door in the library    ok: strict mode refuses every parse
[exit 0]
```

Mode 2 is the one that matters: `FG_JSON_GOOSE_PARSE=1 FG_JSON_GOOSE_REQUIRE=1` turns a decline into an
error, so seven passing texts mean **the Goose parser produced all seven trees**, and the answers match the
nlohmann arm of mode 1. Mode 3 proves the strict mode is not passing by accident when no door is loaded.

Until today that mode had only ever run against `builds/flint-acc/bin`, whose provenance is unknown. It now
runs against a set assembled from two artefacts that each carry half the path, which is what the real build
must eventually do in one go.

## What P10-07 still needs

1. one build that carries **both** halves itself - the recipe is in `P10-07-JSON-ADAPTER-STATE.md`: a bridge
   with an init entry for `goose/json/json-parser.goose`, and the pair registered in `_GOOSE_PAIRS`;
2. then flip `FG_JSON_GOOSE_PARSE` to default, and record the run that justified it.

The swap evidence itself is now complete. What is not complete is the artefact: a set made of two builds is
a laboratory assembly, not a release.
