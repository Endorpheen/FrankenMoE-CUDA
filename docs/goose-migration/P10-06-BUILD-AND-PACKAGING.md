# P10-06: what the build and packaging already do, and what is still missing

Checked 2026-11-19 on `main`, text level, no build.

## Present

| piece | state |
|---|---|
| deterministic unit build | `tools/build-main-runtime.sh` composes the module list, typechecks, generates C, compiles at `-O1` and writes `UNIT_HASH` (the module list plus the SHA-256 of every `.goose`) to `.source-sha256` |
| packaging of the unit | `tools/package-main-runtime.sh` writes `dist/` with `main.goose`, `main.c`, `main.h`, `main.o`, `SHA256SUMS` and `manifest.json`; the dist list, its order, the SUMS bytes and the manifest key order are the Goose decisions in `goose/misc/release-plan.goose`, reached through the prebuilt `build/goose-hosts/pkg` |
| CUDA decisions in Goose | `goose/cuda/cuda-arch-policy.goose`, `cuda-install-layout.goose`, `cuda-target-flags.goose` exist and are composed (their doors are among the twenty accepted components) |

## Missing, and why each is missing

1. **A configure-time decision.** `CMAKE_CUDA_ARCHITECTURES` is fixed in the build command
   (`tools/build-independent-apex.sh:11`, `-DCMAKE_CUDA_ARCHITECTURES=89`). CMake needs it before
   it can generate the build, and the Goose compiler is not a configure-time tool in this
   pipeline: the decision modules exist, but nothing calls them at configure time. This is the
   item the requirement itself names, and it needs a small generated helper or a documented
   two-step (decide, then configure).
2. **Install/dist/release beyond the unit package.** The package above is the composed runtime
   core, not a runnable release: it holds no host, no ggml, no CUDA libraries. The release that
   was published today was assembled from an accepted checkpoint by hand
   (`frankenmoe-release-20261120-exp1476`), and that assembly is not a script in this tree.
3. **A verified clean isolated build with the pinned compiler.** There is no recorded run of
   "fresh clone, pinned compiler, build, compare hash" in this tree; the closest is
   `tools/build-main-runtime.sh`'s own unit hash, which proves the inputs, not the toolchain.
4. **Reproducibility of the generated C.** Nothing compares the C generated by two runs, or by two
   checkouts, byte for byte. The compiler is deterministic in practice; that is not the same as
   checked.
5. **A compile/link manifest audit.** The package records counts (modules, defined and undefined
   symbols) but no audit of what the link line pulls in.

## Consequence for the requirement

P10-06 stays PARTIAL. Two of its items are genuinely blocked on a design step (configure-time
decision) and three on work that has no run recorded here. None of them is closed by the fact that
a release exists: the release proves the artefact, not the reproducibility of making it.

## Next step, in order of cost

1. script the release assembly that was done by hand today, so the packaging item has a command;
2. add a two-run generated-C comparison to the unit build (two `goose --standalone` runs, `cmp`);
3. then the configure-time decision, which needs a decision about where a configure-time helper
   lives before any code is written.
