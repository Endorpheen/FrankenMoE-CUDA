# Three lineages, and the 22 PARTIAL tasks all point at the one nothing builds

Found while picking the next integration from the ledger. It explains why so many tasks have been sitting at
PARTIAL with a single "wire X into host" remainder.

## The three

| lineage | what it is | built by | measured |
|---|---|---|---|
| `runtime/reconstructed` | the Apex path: llama.cpp sources + Goose bridges | `tools/build.py`, `tools/build-standalone-runtime.sh` links its DSO | **yes** - 40.4 tok/s, reference hash |
| `integration/goose-standalone` + `build/goose-main` | the standalone Goose runtime | `tools/build-standalone-runtime.sh` | gates only (v4, graph_exec, tokenizer_decisions) |
| **`runtime/core` (`bmoe_core`)** | the streaming engine | **nothing** | **no** |

`bmoe_core` is referenced by exactly two things, both accounting: `tools/migration-status.sh` (which counts
its functions as superseded/needed) and `tools/sync-goose-tree.py` (which maps experiments to directories).
It has no build target - `find builds -name 'libbmoe_core*'` returns nothing, and no script invokes its
CMakeLists.

The standalone runtime is built from the composed Goose unit plus `integration/m1/host/goose_host.c` and
`integration/goose-standalone/*.c`. **`runtime/core` is not part of it.** The Apex DSO does not link it
either (`ldd` on the shipped libllama shows no bmoe_core).

## Why this matters

Every one of the 22 PARTIAL tasks carries a remainder of the shape "wire X into host" or "replace the call
sites in <file>". Those files are all under `runtime/core/src/`:

```
P9-03  25 call sites in the expert cache, dense placement and row streaming
P9-04  rewrite on_eval to the rh_topk_plan/rh_ask_plan contract
P9-05  wire rts_n_batch/rts_ubatch and the MTP head admission order
P9-07  wire the CSV, decode-trace and route-trace sinks
P9-01  wire validate(), arch_registry.cpp and main.cpp
```

So the outstanding work list targets a lineage that **no artifact is produced from**. Wiring it would change
not one byte of the shipped runtime, cannot be measured, and cannot fail a gate that exercises a binary -
because there is no binary.

That is not an argument that the work is wrong. It is an argument that **its value is currently
unverifiable**, and that the ledger is describing a plan whose target does not exist as a build.

## The decision this needs

One of two, and it is a design decision rather than a measurement:

1. **Give `runtime/core` a build target**, so its wiring is testable and the PARTIAL remainders mean
   something. That is the reading consistent with rule 17's "the universal runtime and the ability to plug in
   architectures" - the streaming engine would become a second artifact.
2. **Retarget the remainders at the standalone lineage**, which is what the project actually ships towards.
   The Goose modules exist and pass their own gates; the host they would be wired into is
   `integration/goose-standalone`, not `runtime/core`.

Doing neither leaves 22 tasks that can be marked complete on inspection alone, which rule 15 explicitly
forbids ("the Goose export must answer, and the native body must be dead code").

## What was NOT done

No build target added and no task retargeted. Adding a CMake target for a 5000-line engine to make a
bookkeeping number verifiable is exactly the kind of change that needs Igor's decision, not an agent's.

## Where the attention did go instead

The Apex path, where every change is measurable: EXP-756 (SLRU policy in Goose, accepted), EXP-757 (the
policy became a parameter with a two-arm gate), EXP-758 (cache size beats policy, so no VRAM trade).
