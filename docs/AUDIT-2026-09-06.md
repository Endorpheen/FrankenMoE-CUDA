# Repeat Audit of FrankenMoE — 2026-09-06

## Summary and Scope of the Audit

A substantial roadmap update is necessary. The main problems are inconsistent sources of the current state, an MTP configuration not reproducible from the root patch, insufficiently strict measurement boundaries, and a premature move from attribution to a complex asynchronous implementation. The most justified new performance target is the bulk prefill time of the patched server. The existing negative CPU/prefetch experiments do not need to be repeated.

Reviewed: the roadmap, README, docs, the full EXP-000–027 journal, individual EXP-028–033 and rejected records, JSON summaries, history.jsonl, saved benchmark/monitor/server logs, CPU microbench/profile reports, the EXP-031 Nsight SQLite, scheduler/CUDA transfer sources, the rejected EXP-033 patch, MTP and hotstore integration, launcher/build/test/aggregation scripts, and key streaming/router/cache paths. This is a documentary and static audit, not a proof of absence of bugs in all of upstream. The server, model, builds, and benchmark were not run; missing raw data was not reconstructed by repeating experiments.

Snapshot: root `main`, HEAD `3c02e5de56061c7c30c45ec325a0d8845639c825`. Before the audit, README and `experiments/EXPERIMENTS.md` had already been modified; EXP-028–033, the input request, and `agents.md` were untracked. `work/llama.cpp-integration` on upstream `4aaad5d...` contains numerous functional changes, including MTP, not just the eight comment edits claimed by the old CURRENT_STATE. User changes were not fixed or reverted.

## Priority Findings

### A1. MTP is not reproducible from the published patch — high priority

`patches/expert-tier-integration.patch` contains safety/hotstore changes but not the MTP `mtp_only`/`model_shared`/speculative port located in the dirty nested source. `scripts/prepare_upstreams.sh` pins `4aaad5d...`; its `integration_present()` checks several marker strings and may declare an arbitrary local mixture to be current. The CMakeCache of the working server points to the integration tree; the exp023 build — `work/llama.cpp-exp023`. A single root SHA does not identify these binaries.

The minimal MTP diff needs to be packaged separately with its provenance, and an isolated clean reconstruction must be verified. Do not modify upstream, do not copy a third-party fork wholesale, and do not extract user comment edits into the deliverable patch. Do not run the existing prepare script to "fix" this: it fetches/checks out upstream trees and does not prove full equivalence of the sources.

### A2. Safety is claimed more broadly than the actual launcher — high priority

`common/common.h` sets `swap_watchdog=false`; `tools/server/server.cpp` starts it conditionally. Neither the default launcher argv nor the MTP command shown in the README contains `--swap-watchdog`; an external env override may change this, so the statement applies to the defaults.

In `scripts/run_qwen38_server.sh`: `sys_rate` is already MiB, but the hard threshold equals `2097152`, while the internal watchdog uses `2048`. Burst VmSwap is compared correctly against `262144 KiB`, but the diagnostic message multiplies by 4, overstating MiB. `wait "$RUN_PID"` under `set -e` can exit before monitor cleanup on a nonzero server exit. Record these defects and fix them in a separate safety stage with synthetic samples, without generating real swap.

The launcher also defaults to `CTX_SIZE=8192`, not 64K/32K; it does not set the historical q4_0 KV/reasoning/MTP flags. «Запусти стандартный launcher» (run the standard launcher) is not sufficient for a comparable baseline. The 8 GiB startup check does not reserve 8 GiB after loading; `EHS=0` does not enable a universal VRAM reservation.

### A3. The volume of transfers is proven, but not the full cause of latency

The EXP-031 GPU duration sum of 1.661 s and the kernel sum of 0.439 s cannot be added to host API/span, subtracted from wall time, with the remainder declared idle: the intervals may overlap. The EXP-032 span of 3.635 s is from the first to the last submission, not a sum of PCIe waits. The 100% applies to the measured sample of backend expert uploads; Nsight also sees other H2D. The EXP-031 text names the units 22.2 GiB, but 22160.56 MiB = 21.64 GiB (23.237 GB).

Offline reading of the surviving `/tmp/exp031b-cuda-prefill-1788632387.sqlite` found 19 218 H2D over the whole session, including startup, and 3706.01 ms of total host `cudaMemcpyAsync` API over the whole session. This is a check that correlation data exists, NOT a new request benchmark and NOT a replacement for the 17 975 in-request calls. Window alignment, correlationId, and union intervals are needed. A new profiler run is allowed only if a specific missing signal cannot be extracted from the saved trace.

### A4. EXP-033 does not prove that two whole-projection buffers will fix the problem

The patch adds a CPU memcpy of the selected ranges, an upload to a temporary device payload, a byte scatter, and an event before reuse. Recording the cause only as event serialization is too strong: gather/scatter/pool allocation costs were not measured separately. Increasing the number of large projection buffers can add hundreds of MiB to tight VRAM and still not remove inter-split waits. `sched->cur_copy` is an index into scheduler copies, not a ring for consecutive projection submissions.

The proposed smaller step: a bounded host ring of direct range copies, without device payload/scatter and ID remap. It tests its own hypothesis (pageable submission/host preparation) and does not guarantee a win. The same stream preserves the copy→compute order; a separate stream is a separate follow-up experiment. All allocator barriers remain until lifetimes are proven. Router N+1 depends on the result of FFN N; "prefetch next layer" is not a ready-made implementation strategy.

### A5. The correctness gate is not yet sufficient for the new async path

`test_small.sh` applies to bmoe-cli, ubatch=8. The EXP-033 candidate guard was `ne[2]>=32`: the existing smoke test may not enter the new path at all. Moreover, Perl extraction can produce two empty files if the output marker changes, and `cmp` would falsely pass. Needed: coverage counters on the multi-token scheduler host→CUDA path, nonempty fixture checks, byte comparison of the selected payloads including MMQ padding, sparse IDs/last expert, forced slot reuse, fallback, cancellation/teardown. `test-backend-ops` alone does not prove scheduler copy lifetime.

An identical short content hash does not prove full routing or MTP rollback. Different hashes cannot automatically be called a near-tie: in EXP-023/024 that explanation comes from the journal without saved margin/logit verification. For a transfer-only candidate, identical settings must preserve tokens/content; a divergence blocks acceptance rather than weakening the gate. Replay forced routes verifies workload identity, not the invariance of router computations.

### A6. Quality and generalizability of the numbers

The historical +13.6% MTP holds, but it is one measured pair, not a five-run median; the EXP-028 JSON contains four warm samples per arm with five matching answers (the fifth is not equal to the fifth measured warm). EXP-033 decode 19.83 vs 20.85: about −4.9%; short 16 tokens do not give a reliable estimate of decode regression. The values of 3.0 s (028) and 4.0 s (033) cross builds/context/cache state; this is not proof of a new regression.

The EXP-024 journal states 311 reused graphs; the saved MTP server log has 104 after the first request and 207 after the second (cumulative); 311 looks like a repeated summation of the counter. Do not use this number for speedup arithmetic.

The EXP-026 history note states 99.9%; the journal — 99.5% inside the main mapping. The arithmetic gives 206114/(85243+124275) = about 98.38%; the global 95.07% is correct. Do not delete the historical records; add a correction. Fault counts do not give per-expert stall durations and do not prove full kernel overlap.

The EXP-019 generic PMU cache-misses cannot, without checking Zen 3 event semantics, be taken literally as LLC line fills and DRAM bytes. A single-core read-only ceiling does not establish the ceiling of the 12-thread server. Cycle shares together with spin are not equal to shares of request wall time. This limits universal conclusions of the kind "cannot give a material win", but does not justify repeating already rejected kernels without new evidence.

### A7. Too-broad closings/reopenings of phases

EXP-027 justifiably closes the unsafe warmer, but one pair and crash correlation do not prove that all of P1 or all residency strategies are useless. EXP-030–032 study a different phase, bulk prefill, so its development is not a repeat of 012/027. The reverse README mistake is to again list io_uring/O_DIRECT/router prefetch without tying them to the new critical path. Exact-adjacency H2D coalescing is already implemented; do not propose it as a new experiment.

Unmeasured graph fusion/barrier reduction, CPU affinity/topology, MTP verification shape-specific kernels, natural long-conversation cache pressure, and limited-gap H2D coalescing remain possibilities but are not in the active queue. A new measured upper bound of the benefit is needed first. Neither low GPU utilization nor the closing of other directions by itself justifies implementing them.

### A8. Preservation of evidence and statuses

The history is spread across docs, journal, JSONL, JSON, and ignored worktrees. EXP-028–033 were not tracked at the time of the audit; a number of raw traces are only in `/tmp`, raw SSE/monitor logs are ignored; some early decisions have only a textual report. `history.jsonl` is not a complete index and contains subsequent retractions: you cannot read only the first entry of an EXP. EXP-026 still begins with PLANNED even though execution is done. The new roadmap is the current order; the old Next experiment entries are historical.

A manifest is needed: artifact path, SHA-256, tracked/local/missing, source/binary/lib identities, argv/env/request, warmup/measured exclusions. A missing file = `MISSING`, not a reason to repeat the experiment. The historical `aggregate_baseline.py` does not verify all hardcoded identity/parameter values and is not a server harness; `test_small.sh` when CUDA is absent finishes with a skip code of 0, which is not the same as the CUDA gate passed.
